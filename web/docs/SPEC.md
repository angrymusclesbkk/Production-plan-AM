## ตัวช่วยหาไซส์

- โหมด "ความยาวเท้า (ซม.)" และ "เบอร์รองเท้า EU"
- ซม.: < 22 → เล็กกว่าไซส์ที่มี (ทัก LINE) · 22 ถึงน้อยกว่า 26 → 22–26 cm · = 26 → ได้ทั้งสองไซส์ (กระชับ/สบาย) · มากกว่า 26 ถึง 30 → 26–30 cm · > 30 → ใหญ่กว่าไซส์ที่มี (ทัก LINE)
- EU: < 35 → เล็กกว่า · 35–40 → 22–26 cm · 41 → ได้ทั้งสองไซส์ · 42–46 → 26–30 cm · > 46 → ใหญ่กว่า
- บรรทัดที่สองบอก Free Size (OG / MAX REP / GRIP): ใส่ได้ถ้าเท้า 24–30 ซม.

## ตะกร้าและสถานะการขาย

เว็บ**ไม่นับสต็อกเป็นตัวเลข** ไม่มีการตัดสต็อก ไม่แสดงจำนวนคงเหลือ ใช้สถานะที่แอดมินกดสลับเองแทน (รายละเอียดกฎอยู่ใน `CLAUDE.md` หัวข้อสถานะการขาย)

- `products.published` (bool) = เปิด/ปิดทั้งรุ่น · `variants.availability` = `on_sale` | `preorder` | `unavailable` (แยกตามสี+ไซส์)
- ตะกร้าเก็บใน localStorage (ห่อ try/catch) — key = sku
- ใส่ตะกร้าได้เฉพาะ `on_sale` เท่านั้น · `preorder` และ `unavailable` ปุ่มพาไป LINE ทั้งคู่
- ตอนกด "ไปชำระเงิน" server ต้องอ่านราคาและ `availability` จากฐานข้อมูลอีกรอบ ห้ามเชื่อค่าจากฝั่ง browser
- ถ้ามีรายการในตะกร้าที่ไม่ใช่ `on_sale` แล้ว (แอดมินเพิ่งปิด หรือตะกร้าค้างมาจากวันก่อน) → ห้ามสร้าง Stripe session ให้ลบรายการนั้นออกจากตะกร้า แสดงข้อความ "สินค้าชิ้นนี้ไม่พร้อมขายแล้ว" พร้อมปุ่ม LINE แล้วให้ลูกค้ายืนยันยอดใหม่
- ไม่มีการจำกัดจำนวนที่ซื้อได้จากสต็อก — จำนวนสูงสุดต่อรายการใช้ค่าคงที่ใน config (ค่าเริ่มต้น 10)
- หลังมีออเดอร์เข้า ถ้าของจริงหมด เป็นหน้าที่แอดมินไปกดเปลี่ยนสถานะเอง เว็บไม่ปิดให้อัตโนมัติ

## ชำระเงิน

- Stripe Checkout (hosted) วิธีจ่าย: `promptpay`, `card` · สกุลเงิน THB · Stripe API รุ่นใหม่ใช้ `allowed_payment_method_types` (ไม่ใช่ `payment_method_types`) ซึ่งเป็นตัวกรองจากวิธีที่เปิดใน Stripe Dashboard — ต้องเปิด PromptPay และ Cards ใน Dashboard ด้วย
- **ไม่มีการตรวจสลิป** — ยอดเงินยืนยันจาก webhook ของ Stripe เท่านั้น
- ห้ามถือว่าจ่ายแล้วเพราะลูกค้าถูกพากลับมาหน้า `/order/[token]` (ลูกค้าเปิด URL นั้นเองก็ได้ หรือจ่ายแล้วปิดแอปไปก่อนก็ได้)

### ยืนยันว่าจ่ายแล้ว — webhook `/api/stripe/webhook`

| Event | ทำอะไร |
|---|---|
| `checkout.session.completed` | ถ้า `payment_status === "paid"` → ออเดอร์ `paid` · ถ้ายังไม่ใช่ → คงเป็น `pending` รอ event ถัดไป — **ห้ามตั้ง `paid` เพราะได้ event นี้อย่างเดียว** |
| `checkout.session.async_payment_succeeded` | ออเดอร์ `paid` (กรณีเงินเข้าทีหลัง) |
| `checkout.session.async_payment_failed` | ออเดอร์ `payment_failed` |
| `checkout.session.expired` | ออเดอร์ `expired` (ไม่จ่ายภายในเวลา) |

กฎของ webhook:

- ตรวจลายเซ็นด้วย `STRIPE_WEBHOOK_SECRET` ทุกครั้ง ไม่ผ่าน → ตอบ 400 ไม่แตะฐานข้อมูล
- **idempotent** — Stripe ส่ง event เดิมซ้ำได้ ให้หาออเดอร์จาก `stripe_session_id` แล้วเช็กสถานะก่อนเปลี่ยน ถ้าเป็น `paid` อยู่แล้วให้ตอบ 200 เฉย ๆ ไม่ส่งอีเมลซ้ำ
- เทียบ `amount_total` ของ session กับ `total` ของออเดอร์ (หน่วยสตางค์) ถ้าไม่ตรง → `needs_attention` และแจ้งแอดมิน ไม่ส่งอีเมลยืนยันลูกค้า
- ตอนเปลี่ยนเป็น `paid` ครั้งแรกเท่านั้น: บันทึก `paid_at`, `stripe_payment_intent_id` → ส่งอีเมลยืนยันลูกค้า → แจ้งร้าน
- ตอบ 200 ให้เร็ว งานที่ช้า (ส่งอีเมล) ห้ามทำให้ webhook ล้มถ้าส่งไม่สำเร็จ ให้ log ไว้แทน

### หน้า `/order/[token]` หลังจ่าย

- ลูกค้าไม่มีบัญชี ลิงก์นี้จึงเป็นทางเดียวที่ใช้ดูออเดอร์ — `token` ต้องเป็นค่าสุ่มที่เดาไม่ได้ (UUID v4 หรือสุ่ม ≥ 128 bit) **ห้ามใช้เลขออเดอร์ `AM-000123` หรือ id ที่เรียงลำดับใน URL** เพราะคนอื่นไล่เลขแล้วเห็นชื่อ เบอร์ ที่อยู่ของลูกค้าได้ (ผิด PDPA)
- หน้านี้ใส่ `noindex` และห้ามอยู่ใน sitemap · แสดงเบอร์โทรแบบปิดบางส่วน เช่น 08x-xxx-1234
- อ่านสถานะจากฐานข้อมูลเท่านั้น ไม่อ่านจาก query string
- `pending` → "กำลังรอยืนยันการชำระเงิน" และเช็กสถานะใหม่เองทุก 5 วินาที นานสุด 2 นาที ถ้ายังไม่ขึ้นให้แสดงปุ่ม LINE พร้อมเลขออเดอร์
- `paid` → "ชำระเงินเรียบร้อย" + รายการสินค้า + ที่อยู่จัดส่ง + "ส่งอีเมลยืนยันไปที่ {อีเมลแบบปิดบางส่วน} แล้ว"
- `expired` / `payment_failed` → บอกว่ายังไม่ได้รับเงิน และปุ่ม "สั่งใหม่อีกครั้ง" ที่ใส่ของกลับเข้าตะกร้า

### บอกลูกค้าก่อนสแกน

- หน้า `/checkout` เขียนไว้ใกล้ปุ่มจ่าย: "สแกนจ่ายด้วยแอปธนาคารใดก็ได้ · ในแอปธนาคารจะขึ้นชื่อผู้รับเป็น **STRIPE PAYMENTS (THAILAND) LTD** ซึ่งเป็นผู้รับชำระแทนร้าน Angry Muscles"

- ค่าส่ง: `[ใส่อัตราค่าส่ง]` — ทำเป็นค่าคงที่ใน config ให้แก้ง่าย (เช่น ค่าส่งเหมาจ่าย และส่งฟรีเมื่อยอดถึง X บาท — รอเจ้าของร้านกำหนด)

## ฐานข้อมูล (Supabase)

- `products` (slug, name, subtitle, category, price, unit, material, features jsonb, size_note, size_chart, image_bg, **published bool**, sort)
- `variants` (sku unique, product_slug, color, color_hex, size, **availability** enum `on_sale`|`preorder`|`unavailable` ค่าเริ่มต้น `on_sale`, image, note) — **ไม่มีคอลัมน์ stock**
- `orders` (id, number เช่น AM-000123, view_token (unique, สุ่ม, ใช้ใน URL), status: pending / paid / payment_failed / expired / packed / shipped / cancelled / needs_attention, customer_name, phone, email (not null), address jsonb, subtotal, shipping_fee, total, stripe_session_id (unique), stripe_payment_intent_id, tracking_no, carrier, created_at, paid_at)
- `order_items` (order_id, sku, name, color, size, qty, unit_price)
- Row Level Security: ลูกค้าอ่านได้แค่สินค้า (เฉพาะ `published = true`) · ออเดอร์อ่าน/เขียนผ่าน server เท่านั้น · เขียน `published` / `availability` ได้เฉพาะแอดมินผ่าน Supabase Auth
- seed จาก `data/products.json`

## แอดมิน (`/admin`)

- ล็อกอินด้วยอีเมล (Supabase Auth) · อนุญาตเฉพาะอีเมลที่อยู่ใน env `ADMIN_EMAILS`
- ออเดอร์: รายการล่าสุด กรองตามสถานะ · เปลี่ยนสถานะ · ใส่เลขพัสดุ · พิมพ์ใบแปะหน้าแบบง่าย · export CSV
- สินค้า: แก้ราคา · สวิตช์เปิด/ปิดทั้งรุ่น (`published`) · ตั้งสถานะการขายทีละตัวเลือก
  - ตารางตัวเลือกจัดกลุ่มตามสี แต่ละแถวมีปุ่มเลือก 3 ค่า (segmented control) พร้อมขนาดแตะ ≥ 44px: **พร้อมขาย · รอพรีออเดอร์ · ยังไม่พร้อมขาย** — สีพร้อมขายใช้เขียว, พรีออเดอร์ใช้เหลือง, ยังไม่พร้อมขายใช้เทา (มีข้อความกำกับด้วย ไม่พึ่งสีเพียงอย่างเดียว)
  - ปุ่มลัดระดับสีและระดับรุ่น: "ตั้งทุกไซส์ของสีนี้เป็น …" และ "ตั้งทั้งรุ่นเป็น …" เพื่อไม่ต้องกดทีละ 55 แถว
  - บันทึกทันทีเมื่อกด (optimistic UI) พร้อมข้อความ "บันทึกแล้ว" และปุ่มเลิกทำ · ถ้าบันทึกไม่ผ่านให้เด้งค่ากลับและแจ้งเตือน
  - หน้าร้านใช้แคช: แอดมินแก้แล้วล้างแคช (`updateTag` + `revalidatePath`) และเปิดหน้าล่วงหน้าให้ทันที · ถ้ากดรัวจนชนกัน แคชหมดอายุเองทุก 60 วินาที (`cacheLife`) · หน้าชำระเงินอ่านฐานข้อมูลสดเสมอ
  - เก็บ log ว่าใครเปลี่ยนอะไรเมื่อไหร่ ในตาราง `availability_log` (sku, from, to, admin_email, at)
  - นำเข้าจาก CSV: คอลัมน์ `sku, availability` (ไม่ใช่ stock แล้ว) · แถวที่ sku ไม่ตรงให้รายงานกลับ ไม่ข้ามเงียบ ๆ
